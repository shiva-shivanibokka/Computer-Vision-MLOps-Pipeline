Six ways a circuit board can be wrong.

This is a YOLO detector that looks at a photograph of a printed circuit board and marks the manufacturing defects on it — missing holes, mouse bites, open circuits, shorts, spurs, spurious copper.

The detector is not the interesting part. The loop around it is. Every training run is tracked, every model version has to beat the one in production before it is allowed to replace it, every prediction is logged, and drift in those logs triggers a retrain. Three versions earned promotion. One was refused. You can see all of it here.

The model in front of you finds roughly a third of the defects on a board. That is a real number from a real dataset, and the Limits tab explains exactly why it is not higher — because a portfolio that only shows the parts that worked is not showing you engineering.

How to read this panel

Five tabs follow this one. They are ordered the way the system actually runs: you score a board, you see which model version scored it and why that version won, you watch what the served traffic looks like over time, and then you read what the whole thing still cannot do.

Inspect

The demo. Pick one of six boards — one per defect class — or upload your own. The model runs and draws a solid gold box around everything it found.

For the six shipped boards there is also a dashed rose box for every defect the model missed, because those boards come from the labelled validation set and the answers are known. The counter reads found 4 of 6, not just 4 detections. An uploaded image has no labels, so misses cannot be shown for it — only what the model claims to see.

Registry

Four model versions and what happened to each. The promotion gate compares a new version against the incumbent on mAP50-95 and refuses anything that does not beat it. v1, v2 and v3 cleared it. v4 did not, and was never served.

The row marked production is the model that scored your board on the Inspect tab — the panel checks that against the live server rather than trusting the table.

Drift

Every prediction made through this panel is logged — image statistics plus what the model returned, never the image itself. Evidently compares the recent window against a reference sample from the training set, and if enough feature columns drift, a scheduled GitHub Action retrains.

The counter starts at zero on every container restart. That is honest rather than broken: the log lives in the container's own storage, so a free Space that goes to sleep forgets it.

Limits

Why mAP@50 is 0.336 and not 0.9. The short version is that this dataset is resolution-limited, and the tab shows the evidence for that claim, plus the tiling experiment that was supposed to fix it and instead failed badly.

API

The endpoints behind the panel. Everything here is an ordinary HTTP call — nothing on this page is pre-rendered or faked, and you can reproduce any of it with curl.

What you are actually talking to

one container, no attached services

A single FastAPI process on a free Hugging Face Space. It holds the YOLO weights, the API, and these three static files — no build step, no database, no external service that can quietly expire. The one cost is that the Space sleeps when nobody visits, so the first request after a quiet spell waits for the container to wake and the weights to load.

The promotion gate

promote on mAP50-95

A trained model does not become the served model by existing. It has to beat the version currently holding the production alias on the gate metric, and the margin is 0.0 — so a tie does not promote either.

This is the part that people skip. Without it, "we retrained the model" and "the model got better" are the same sentence — and as v4 below shows, they are not.

How the retrain loop closes

evidently · scheduled action

A scheduled GitHub Action pulls the recent prediction window and compares it against a reference sample drawn from the training set. Evidently reports which feature columns have drifted; if the drifted share crosses 0.5, the workflow retrains, the new run is registered, and the gate above decides whether it is allowed to serve.

That is the whole loop: serve → log → detect drift → retrain → gate → serve, with a human required at exactly zero of those steps and a model blocked at the one step that matters.

Being straight about this one. The prediction log lives in the container's own filesystem, so when this free Space sleeps, the log goes with it. The loop is wired end to end and the drift check runs, but on a demo like this it is running against a window that starts fresh each time the container wakes. Persisting it needs a volume, which is a paid Space feature.

Why it finds a third of the defects

mAP@50 0.336 · recall 0.355

A defect on these boards is about 70 pixels across on a 3000-pixel photograph — roughly 2.4% of the width. The detector runs at 1280, so by the time the board reaches the network that defect is around 30 pixels. There is very little left to look at.

The evidence that this is a resolution ceiling and not a training problem is in the registry: v2 and v3 use the identical model and image size, and v3 had three times the epochs. It bought 0.311 → 0.336 on mAP50. Three and a half hours of GPU time for two and a half points, with early stopping kicking in around epoch 174. The curve is flat. More of the same would not help.

The experiment that failed

The standard answer to tiny objects is tiling — slice the board into 640px tiles so each defect fills more of the frame, detect on tiles, stitch the results back. It was built and it did not work. Sliced inference over a full board found 1 defect out of 18.

The cause was in the tile set, not the idea: 32% of generated tiles contained no defect at all. Trained on that, the model learned the cheapest correct answer available — predict nothing. It was refused by the gate and never served. The code is still in the repo behind tiling.enabled: false, with the fix noted: drop background tiles from 15% to about 3% and rebuild.

What I would do next

Retry tiling with the background ratio corrected, which is the change most likely to move the number. Failing that, imgsz: 1536 on full boards is the low-risk option and would give a modest gain. Either way the gate decides, not me.

Honest scope

This is one public dataset, 693 boards, six classes, trained on a single 8 GB consumer GPU. It is a working demonstration of the engineering around a model, not a production inspection system, and a real line would want far more data, a much higher-resolution camera rig, and a recall target set by what a missed defect costs.
